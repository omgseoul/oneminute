# Guest web check-in

The QR settings page has a second built-in item, `웹체크인 (Beds24 연동)`. It starts disabled. In its settings, an authenticated owner runs today's arrival diagnostic, selects the actual password field, chooses the local release time (initial value 15:00), and saves. A diagnostic lists only counts and source field identifiers; it does not return guest names or passwords. An unverified source cannot be enabled.

The guest completes three steps: reservation name, exact check-in/out dates, and exact booking confirmation number. Verification happens together on the server. After Unicode/accent/spacing normalization, the complete name in either first/last order must have at least 0.95 normalized Levenshtein similarity. The number must exactly match Beds24's booking ID or channel `apiReference`. Name/date alone and a booking number with a different name cannot disclose access information. Real guest names are never offered as multiple-choice answers.

Only today's new/confirmed reservations qualify. Multiple matching reservations, multi-room quantities, missing/ambiguous assigned units, cancellation, conflicting password items, unavailable provider data, or disabled QR settings fail closed to staff help. The booking and current release settings are rechecked before returning one assigned room and its access code.

Supported explicit password sources are booking `infoItems[].text` identified by its exact `code`, and assigned-unit `name2` through `name8`. The owner must identify which field really contains the password. Free-form notes are not scanned for numbers. Accepted codes are 4–32 ASCII letters/digits, `*`, `#`, or `-`; unsupported formats require staff assistance. Other booking info items and other units never reach the guest browser.

The existing Beds24 credential/refresh and shared rate-limit path is reused internally. No credential is returned to clients, and the diagnostic/verification paths do not write codes into the ordinary booking cache. Public clients cannot execute the service-only RPCs. Verification counts every attempt before provider access (20 per IP and 100 per property per 15 minutes); admin probes are limited to five per ten minutes. Guest responses use no-store. The UI clears input and access details on close/page exit and clears results after five minutes.

Release order: apply `guest_web_checkin.sql`, deploy the existing `beds24` Edge Function including `web-checkin.mjs`, then publish the QR pages. Keep activation off until an authenticated owner confirms the real source field with the diagnostic. Local synthetic tests verify matching, authorization, rate limits, canceled/ambiguous bookings, source isolation and mobile layout; they do not prove that a property's real provider password field is populated.
