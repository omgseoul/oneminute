# Online management (Beds24)

The owner home footer opens `online.html`. Owner sessions are validated server-side for the selected OMS property. The home property is allowed; a shared property requires both approved property_settings and messages permissions on every request. Shared attendance access alone does not grant access to guest reservations. The header selector changes all online views and webhook labels together; the Beds24 mapping select is only for first-time setup and becomes fixed after saving. Unconnected branches can explicitly reuse an authorized existing Beds24 credential without a second invite code. Credentials remain in Vault; reconnecting a shared credential detaches only that branch. Each OMS property maps to one Beds24 property. The same Beds24 property cannot be registered twice.

Setup: paste a new V2 invite code in Basic information, connect, select the matching property, save, then copy the generated URL into Beds24's Version 2 Booking webhook setting. Preserve Make's existing URLs. Tokens are exchanged server-side, encrypted in Supabase Vault, and never returned to browser storage. Refresh occurs before expiry, including idle connections through the worker. Secrets are not committed or logged.

Cached lists support arrival date, reservation creation date in the property's timezone, and guests staying overnight (arrival <= date < departure). API pagination is consumed, and queries cover at most 93 days. Lists display up to 2,000 rows; narrow larger searches. Room/unit names come from the connected property. Card/payment fields are deliberately not stored.

Messages are fetched from Beds24 with the selected property filter. Webhook data is a change notification only: the server reads the authoritative booking/message via the API before storing it. A durable queue retries failed fetches, deduplicates message IDs, and preserves events arriving while a worker runs. Incoming guest messages create owner bot notifications that open the online conversation. The message screen reads cached updates every 12 seconds while visible. Attachments are indicated by name; open the original in Beds24. API/channel limitations are surfaced as errors.

All sends require an explicit owner action. A persistent outbox ID prevents double clicks and repeated HTTP requests from resending. Ambiguous network failures become `uncertain`; they are never automatically retried. Check the OTA conversation before starting another send. Manual sends and approved AI replies are recorded with actor, status and timestamps.

AI is off by default. Approval mode generates a draft on new webhook-driven conversations, using the property's existing DATA, prompt, escalation classification and provider. It never sends without approval. Freshness is checked against the latest imported message, including other host replies; obsolete approvals are blocked. The shared wallet reserves credit before inference, settles once, and records tokens, sources and disposition. Interrupted jobs settle as estimated and remain visible. AI with attachments requires human review. Existing Make auto replies are independent: operators must avoid approving a second answer to an already answered inquiry.

Deploy `supabase/setup/beds24_online.sql`, deploy `beds24` with its guest-ai module dependencies, and deploy the extended `dispatch-notification` function. Functions authenticate requests internally (owner session / webhook capability / worker secret). All online RPCs and private tables are inaccessible to anon/authenticated roles. Production confirmation still requires an owner-entered valid invite code and a real inbound webhook; tests use isolated fixtures and do not send to actual guests.

Future autonomous mode must be a separate server-side policy with opt-in, takeover suppression, escalation recipients, duplicate prevention across Make, and auditability. This release intentionally exposes only off/approval modes.

Booking and inbox state chips allow multiple selections. Defaults include new, confirmed, request and inquiry; cancelled, black and unknown are opt-in. Filtering happens before SQL limits and is mirrored in the UI. Inbox refresh hydrates reservation metadata (including cancellations) with the API V2 batch ID query. Deploy the additive function replacement in `supabase/setup/beds24_online_branch_filters.sql` before the updated beds24 function and frontend; existing webhook URLs and data remain intact.

## Translation allowances (2026-11-13)

- Operator Center → Translation stores the shared Google Cloud Translation Basic v2 key in Vault. A minimal `OK` translation verifies API/billing access before replacing a saved key; failed candidates never overwrite the existing key. Verification uses two provider characters, outside customer allowances. Saved keys can be rechecked without exposing them.
- All plans initially include 50,000 input characters/property/month. Operators can edit each plan and override an individual customer's monthly allowance. Calendar months use Asia/Seoul. Read-only service summaries and Property → Data Management display shared usage, remaining/reserved amount, and personal-key usage.
- Common key is used while an entire request fits in the remaining allowance. Otherwise a registered personal key is used (the customer pays Google); no OMS AI credits are deducted. No silent common-key overage. If common translation is unavailable/unconfigured, the explicitly registered personal key can be used.
- Cache identity is property + booking + original body hash + target + incoming/outgoing. Cache hits are free; existing successful incoming translations are retained. Per-property advisory locks and reserved characters prevent concurrent requests from overspending. Rejected provider calls release reservations; ambiguous timeouts/5xx and lost workers conservatively settle the reservation once. They do not automatically retry.
- 80% and exhaustion create monthly-deduplicated system notices through the same owner/bot delivery mechanism as storage warnings. Scheduled service checks also catch thresholds after a plan change.
- Incoming messages translate to Korean, inline. Outgoing replies offer a compact custom language selector and a preview step; automatic language uses the latest guest message's detected language. If it is not known, select a language explicitly. Translation never sends messages. Only `번역본 보내기` invokes the existing idempotent send flow. The server validates translation ownership/booking/body, stores the original and target on the outbox, and exposes the original beside the matching sent message and in logs.
- Apply `supabase/setup/translation_allowance.sql`, then deploy Beds24 with `translation.mjs` alongside the existing entrypoint and guest-AI dependencies, then publish the frontend. No browser or customer RPC can read provider keys, select a billed provider, or alter usage counters.


## Inbox stay, read and reply filters

Apply `supabase/setup/beds24_inbox_followup.sql` after the inbox and translation setup files, then publish `online.*`. The patch preserves the current owner authorization and translation code. Its two private helpers use invoker permissions and remain inaccessible to browser roles.

The stay picker uses each property's local calendar day: check-in is arrival today; staying is arrival before today and departure after today; check-out is departure today; other is none of those (including unknown dates). Multiple selections use OR. Unread and unanswered switches use AND with the selected stay/status/direction/message-date filters, before pagination. The menu badge continues to count incoming unread messages in the saved message period.

Reply state compares the latest incoming message against later host messages across the stored conversation, including messages outside the chosen period. Confirmed `sent` outbox rows also count while sync is pending; drafts, failures, uncertain deliveries and internal notes do not. A newer incoming message makes the conversation unanswered again. Host-only conversations are neither replied questions nor unanswered questions.

Expanding an incoming message marks incoming messages through its `(sent_at,id)` position as read within the same property/booking. Newer arrivals remain unread. When an open card stops matching the unread/unanswered filter after reading or sending, it stays visible until collapsed; changing filters clears that temporary retention. Reading and filtering query the stored inbox and do not request extra Beds24 syncs.


## Incoming translation language

After the existing inbox and translation setup, apply `supabase/setup/beds24_translation_language.sql`, deploy Beds24 with its existing dependency set, then publish `online.*`. The default incoming translation language is stored per property (Korean initially) and saved via the same authorized owner action. Incoming cache identity includes target language; outgoing `auto` continues to use the guest's detected source language.

Known same-language incoming text returns silently before reserving translation allowance; plain Hangul-only text also bypasses the provider for Korean. Unknown language uses the provider's detection, stores the result once, and hides a duplicate translation when source and target match. A first detection may still incur the provider's normal character usage. Outgoing translation remains an explicit preview and separate send action in both inbox and full conversation forms.

## Reservation occurrence feed and same-day notifications

Deploy `supabase/setup/beds24_booking_data.sql` after the preceding online migrations, then deploy Beds24, dispatch-notification and guest-ai with their existing dependencies, and publish the frontend. Online management orders Messages second and adds 예약 Data after Check-in Search. The shared multi-property picker scopes stored reads and counts; the default period is the last seven local calendar days. Query/refresh hydrates Beds24 by booking creation time through the existing shared sync lease and cooldown. Reads and polling do not make provider calls.

Rows are newest first, single-line and expandable, with a three-character branch and the existing channel icon/popover. Red 당일 and pink 내일 compare arrival against the property's local booking creation date, so historical flags remain meaningful. Cancelled entries use a neutral cancellation tag. The menu counter always counts active bookings created today and arriving today, independently of the viewed period.

A private insert/update trigger records each qualifying same-day booking once. It creates notices only for new eligible events on the current local day, excludes cancellations/blocks/inquiries, and does not replay unchanged imported records when settings are enabled. Existing webhook imports and explicit booking refresh both use this path; pending notice IDs are drained through the existing idempotent push dispatcher, including booking-only worker retries. Basic Information stores enablement, employee/admin recipients and their four notification strengths per property. Employees must have an active, unexpired working session with an actual check-in report and no checkout; dispatch rechecks they are still working. Active property administrators are independent recipients. Owner bot cards link to the matching branch's reservation detail; staff cards show the notice contents without opening owner-only screens.

AI escalation now explicitly rejects tone-only emergencies. A narrow deterministic guard demotes model-generated urgent classifications of greetings, thanks, “뭐하냐” and impatient reply requests, unless recent conversation context contains an actual incident. Property-specific routing and explicit alert rules retain precedence. This changes future classifications; historical alerts are not rewritten.

## Booking filters and opt-in automatic translation

Apply `supabase/setup/beds24_auto_translation.sql` after the booking feed and incoming-language migrations, deploy Beds24 with its unchanged dependency set, then publish `online.*` and `translation-languages.js`. Booking Data reuses the message period-picker layout with its own saved seven-day default and a maximum 93-day range. Reservation status is filtered in SQL before pagination and shares the existing multi-status control. The menu's same-day counter stays independent of the feed period/status selection. Redundant in-view back links are removed; the shared header retains parent navigation.

Automatic translation is initially off for every property. Basic Information saves opt-in and excluded source languages per property through the authorized owner path. The picker initially lists major languages and selected entries; searching covers the full NMT language catalog, with Korean labels from Intl.DisplayNames and documented English fallbacks. Multiple selections survive search changes and save with Done; closing without Done discards draft changes. Disabling automatic translation keeps exclusions for later reuse. Manual translation remains available for every excluded language.

Automatic translation runs for expanded incoming inbox cards and visible guest messages in the full conversation, with at most two in-flight requests and per-body/target/settings deduplication. Polling and re-rendering reuse completed work, failed automatic requests have a two-minute cooldown, host messages are not automatically translated, and manual results take precedence. Original text is preserved. The server independently rechecks opt-in and source-language exclusions before reserving a translation, including changes made while detection is pending.

Known source languages reuse prior successful jobs. If an exclusion is configured and source language is unknown, Basic v2 `/detect` runs first; excluded messages do not go to `/translate`. Detection is stored in a separate incoming job whose reserved target is `und`; its translated field is the detected language code and it is never an outgoing preview. This uses the same existing allowance/reservation/settlement logic and does not consume AI credits. Standalone detection is billable character processing, so detection characters count toward allowance; a permitted unknown-language message can incur one detection and one translation. Help text explains this, and cached detection/translation is not charged again. Same-language bypass, ambiguous-timeout accounting and manual translation cache identity remain intact.

Language-code source: https://cloud.google.com/translate/docs/languages (NMT table, checked 2026-11-13). Detection contract: https://cloud.google.com/translate/docs/reference/rest/v2/detect. Metering: https://cloud.google.com/translate/pricing.

## Basic information card accordions and active online-message alerts

Basic Information uses six native details/summary cards with one-line descriptions. All start closed and open independently. Webhook and translation help buttons appear only in expanded headings; opening help does not collapse the card. Existing connection and translation controls remain available inside their cards.

Apply `supabase/setup/beds24_message_alert_draft.sql` after the earlier migrations, then `supabase/setup/beds24_message_alert_routing.sql`, deploy Beds24 and dispatch-notification, and publish the frontend and notification bot script. Previously saved preferences are copied into the active per-property `online_message_alert` field without resetting them. The owner-authorized `save_message_alert` action validates and immediately saves active preferences; the older draft-named action remains a compatible alias for clients loading older scripts. The UI shows unsaved changes distinctly and prevents edits while a save is pending.

Staff and administrators have independent enablement, strengths and guest-date scopes. Scope selections use OR: arrival today, arrival before today/departure after today, departure today, or all (including other/unknown dates). Each property's timezone defines today. Working staff require an active employee and working, unexpired session with a check-in report at or before dispatch and no checkout. Administrator enablement, scopes, optional local time window and optional no-working-staff condition use AND. Time starts are inclusive and ends exclusive; overnight windows span midnight. No-staff checks actual reported duty even if staff notifications are disabled.

Only newly imported eligible guest messages create notice recipients. Duplicate imports and changes to settings do not replay messages. Inbox storage/unread state is independent of alert suppression. Dispatch intersects original recipient records with current eligibility, so it rechecks working status, time, scopes and enabled state without adding recipients who became eligible later. The configured strength is used for each recipient: weak, normal, strong or explicit urgent. Weak continues through the existing Android status-notification path with no fullscreen popup. Home inbox polling exposes `online_popup_allowed` for each authorized notice and the popup queue respects it before either the browser dialog or native bridge; weak and currently ineligible online notices remain in history and unread counts without a second popup. Same-day booking alerts and AI escalation retain their independent configuration.

Existing fullscreen receipt layouts are unchanged. New staff notices open the staff-authorized message detail instead of an owner-only online page; owner links preserve the booking and property.
