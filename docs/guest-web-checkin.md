# Guest web check-in

The QR settings page has a second built-in item, `웹체크인 (Beds24 연동)`. It starts disabled. In its settings, an authenticated owner runs today's arrival diagnostic, selects the actual password field, chooses the local release time (initial value 15:00), and saves. The owner-only diagnostic now displays up to 100 actual names, channel booking numbers, internal IDs and stay dates. Password values are never returned. Only counts and field identifiers are persisted; the UI escapes all values and clears samples on page exit. An unverified source cannot be enabled.

The guest completes three steps: reservation name, exact check-in/out dates, and booking confirmation number. Verification happens together on the server. After Unicode/accent/spacing normalization, the complete name in either first/last order must have at least 0.95 normalized Levenshtein similarity. Internal Beds24 IDs match exactly; channel apiReference accepts at least 90% string similarity after spacing/hyphen normalization. These scores are string similarity, not identity confidence. A strong name plus near-matching reference passes directly. A weaker reference requires staff verification: name/date plus a multiple-choice guess cannot safely replace booking proof.

Only new/confirmed arrivals in the configured access window qualify: by default arrival-day 15:00 through the next day 11:00, property local time. The end time is configurable up to 11:00. At midnight the original arrival date still works; provider queries use that validated date. Overnight admin probes select the preceding arrival day before the new start time. Multiple matching reservations, multi-room quantities, missing/ambiguous assigned units, cancellation, conflicting password items, unavailable provider data, or disabled QR settings fail closed to staff help. The booking and current release settings are rechecked before returning one assigned room and its access code.

Supported explicit password sources are booking `infoItems[].text` identified by its exact `code`, and assigned-unit `name2` through `name8`. The owner must identify which field really contains the password. Free-form notes are not scanned for numbers. Accepted codes are 4–32 ASCII letters/digits, `*`, `#`, or `-`; unsupported formats require staff assistance. Other booking info items and other units never reach the guest browser.

When the name differs but the channel reference is at least 90% similar (minimum six characters), one real matched reservation name and 14 synthetic names are offered. Other arriving guests are never used as decoys. Choices use cryptographic randomness, opaque IDs and script-aware generation; unsupported scripts require staff help. One set per reservation is stored server-side, bound to a session token and reservation fingerprint. Repeated requests shuffle the same labels to prevent intersection attacks. Two different wrong selections lock the challenge; retries of the same selection are idempotent. Refresh, new devices, copying a displayed name into the first step or waiting for expiry cannot reset attempts. Challenges expire after ten minutes. Records older than three days are removed for that property on subsequent verification requests. No room inventory or codes are returned before successful identity verification.

The existing Beds24 credential/refresh and shared rate-limit path is reused internally. No credential is returned to clients, and the diagnostic/verification paths do not write codes into the ordinary booking cache. Public clients cannot execute the service-only RPCs. Verification counts every attempt before provider access (20 per IP and 100 per property per 15 minutes); admin probes are limited to five per ten minutes. Guest responses use no-store. The UI clears input and access details on close/page exit and clears results after five minutes.

Release order: apply `guest_web_checkin.sql` followed by `web_checkin_overnight_choice.sql`, deploy the existing `beds24` Edge Function including `web-checkin.mjs`, then publish the QR pages. Keep activation off until an authenticated owner confirms the real source field with the diagnostic. Local synthetic tests verify matching, midnight/11:00 boundaries, two attempts, replay/refresh/device lockout, authorization, rate limits, canceled/ambiguous bookings, source isolation, owner-only escaped diagnostics and 320/390/412px mobile layouts; they do not prove that a property's real provider password field is populated.
