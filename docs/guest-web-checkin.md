# Guest web check-in

The QR guest menu shows `웹체크인`. The existing owner-only settings select an explicitly verified Beds24 password field and a property-local access window (default arrival day 15:00 to the following day 11:00). Owner diagnostics display actual names, channel references, internal IDs and stay dates, but never password values. Only diagnostic counts/source identifiers are persisted.

## Reference-first flow

1. Enter the booking number (up to three attempts), or use the `모름` button. A mismatch keeps the input open until the third failed attempt. Skipping or exhausting the three attempts starts the document route with date input. A unique active reservation is selected from the currently allowed arrival days. Channel references accept at least 90% normalized string similarity; sequential internal Beds24 IDs require an exact match. The response reveals no guest name, date, room or code.
2. Enter exact check-in and check-out dates. Two wrong date submissions lock that reservation's verification. The count is server-side and cannot be reset with another session/device. Duplicate request IDs with identical input are idempotent. The edge binds each attempt ID to its input values so reusing an ID for a different guess still counts.
3. Select the name from ten options: one matched reservation name and nine synthetic names. Other guests are never used as decoys. The server maintains one cryptographically generated set and shuffles its order, preventing repeated-list intersection attacks. Two wrong distinct choices require staff assistance. A successful selection returns a greeting, assigned room and access code.

## Unrecognized-reference flow

After three reference failures or `모름`, the guest first enters check-in/out dates, then a name. The dates are persisted server-side. Pressing Next on the name step checks only arrivals on that selected check-in date; a client cannot override the date in the name request. A normalized full-name similarity strictly greater than 90% is required. No matching name returns `예약명단에 없습니다. 이름을 확인해주세요.` and the remaining count. Three failed name submissions block that property/device identifier on the server. The client also remembers the blocked state. Changing a session token or refreshing cannot reset it.

Device identity is a random browser-local identifier stored in localStorage, not a hardware fingerprint. Different browsers or cleared browser storage cannot reliably be recognized as the same physical device. Existing IP/property rate limits provide additional protection. Blocked device records persist; ordinary verification cannot unblock them. Names entered incorrectly are not stored in the device record.

After a name passes, the already selected dates identify one reservation. A wrong checkout date is counted against the existing two-attempt date limit and returns the guest to the date step. Ambiguous reservations require staff help. Date errors share the two-attempt reservation limit. The guest then uploads a booking-confirmation screenshot containing the name, reference and both dates. The browser re-encodes JPEG/PNG/WebP to JPEG, strips metadata, limits the longest dimension to 2200px and the transmitted image to 2MB. The server accepts only bounded base64 image data with matching magic bytes; no external image URL is fetched.

The existing AI provider connection is used through its normal server-side credential helper. The Responses API request uses gpt-6-luna, low reasoning, strict JSON output, store=false and no tools. The model sees only the screenshot and extraction instructions, never the real reservation list or door codes. Image text is explicitly untrusted. The server requires readable fields, a name score greater than 90%, exact dates, and an exact extracted channel/internal reference for the bound live reservation. It rereads the booking after extraction. Missing, conflicting or unreadable fields, wrong references, canceled/changed reservations, provider errors and timeouts fail to `직원과의 채팅으로 예약을 확인하여 주십시오.`. Screenshot extraction cannot establish that an image is an authentic, unaltered document.

One image check is atomically claimed per reservation, with a property limit of 30/day to bound public AI usage. Replays cannot generate duplicate AI calls. Images and extracted document text are not persisted in OMS or logged. Verification-session names expire after twenty minutes, are cleared on completion/failure, and expired rows are purged on later requests after one day. Booking guards/decoys are purged after three days on later requests. Persistent device lock records contain only hashed random identifiers and attempt IDs.

## Release and isolation

Each step is enforced by the service-only `web_checkin_flow` RPC; client-provided stage, IDs, scores or fake AI approval cannot skip verification. Sessions bind property, device, selected dates, booking fingerprint and expiry. Reference attempts persist in the session and opening the dialog restores its current stage and counts. The fingerprint includes name, reference, dates, assigned room and unit. Existing failed legacy name challenges stay locked. Old clients must refresh rather than falling back to the previous release route.

Only new/confirmed single-room reservations inside the time window are eligible. The provider query uses the validated arrival day, so a November 16 arrival remains accessible early on November 17. Before disclosure the server rereads the booking and state, resolves exactly one assigned unit, then checks live QR enablement, source and time again. Explicit password sources are exact infoItems codes or assigned-unit name2 through name8; conflicting codes and missing assignments require staff help. Free-form notes are not scanned. Responses are no-store; the UI clears inputs/images/results on close or page exit and clears access results after five minutes.

Private tables use RLS and deny anon/authenticated access; RPCs are service-only. Provider credentials never reach a client. The existing 20/IP and 100/property requests per fifteen minutes remain in force. Bounded body parsing permits larger bodies only for the upload step.
