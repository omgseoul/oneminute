# Guest automatic messages

Guest message → Auto → select one property → + 자동메시지 추가. Settings use an accordion list; completing the editor opens the title dialog. The inbox retains its existing multi-property filter, while automatic-message settings allow exactly one authorized property and never All.

Each rule stores a required common template and optional nationality-specific versions. Buttons insert `{{이름}}`, `{{체크인}}`, `{{체크아웃}}`, `{{비밀번호}}`, `{{객실}}` at the caret. Country uses Beds24 country2/country, never inferred names. Unknown/missing countries and unconfigured language versions use common. The password is the uniquely assigned room booking's `LOCK_PIN`; missing/conflicting codes fail the delivery without sending, preserving leading zeroes for valid codes. Raw provider data and names are not modified.

Reservation rules use bookingTime for instant delivery. Booking-after requires at least 1 day and uses the property-local booking date + N days at the selected clock time. Check-in offsets use property-local date and configured clock time (default 09:00). The existing authenticated Beds24 minute worker claims up to four due jobs per invocation. New and confirmed bookings in the existing Beds24 cache are eligible; webhooks already hydrate that cache. Before sending, the worker re-fetches booking status, country, room assignment and PIN, then rechecks the rule revision and pause state. No rule is installed/enabled by deployment.

Rules apply to future due times after activation. Missed execution can catch up within 24 hours, but old due times before activation/resumption are not sent late. Active/future reservations that miss this boundary create a deduplicated administrator bot notice. For check-in-before rules only, if the scheduled time was already past at booking receipt, the effective due time is the booking timestamp. This allows same-day and last-minute bookings made after rule activation to send immediately after synchronization. The 24-hour execution window runs from that effective due time; old bookings before activation and previously terminal receipts are not revived. Each rule/booking pair can send once; ambiguous network outcomes are marked uncertain and never automatically resent. The property-scoped history displays results and booking IDs without storing rendered PINs in this feature's logs. Existing Make/Beds24 automations are independent and should be coordinated by the operator.

Schema: `supabase/setup/guest_auto_messages.sql`, `auto_message_exception_alerts.sql`, `auto_message_required_values.sql`, `auto_message_targeted_retry.sql` and their matching migrations. Private RLS-enabled tables; public RPC wrappers execute only as service_role. Configuration RPC validates a live owner session and both messages/property-settings permissions for shared properties. No provider delete or inventory mutation is introduced.

Validation: `tests/online/auto-messages-database.cjs`, `auto-messages-edge.mjs`, `auto-messages-ui.cjs` (320/360/412px), and existing inbox/edge regression tests. Network sends use fixtures in tests; no guest receives test messages.

Exception alerts: the independent DB minute watchdog scans known reservations and stale delivery leases. It records missed timing, missing schedule metadata, elapsed retry windows and worker backlog. Required-value omissions, conflicting PINs, malformed variables, and pre-send API/permission/connection errors now create terminal failed receipts without automatic retry. Only variables actually used in the selected template are required. Every missing field is named together; controlled lookup-stage errors omit raw provider responses and secrets. Expired pre-send leases also fail. Channel rejection, cancellation and ambiguous results keep their existing terminal handling. Each delivery attempt has at most one delay notice, one terminal notice and one recovery notice. Intentional rule pause produces no error notification. Home and shared managers with both messages/settings access receive notices; push revalidates that access. Notices use the existing authenticated, per-recipient idempotent bot push transport; rendered guest PINs are never copied into alerts.

Manual retry: failed deliveries show the guest name, room, booking/channel reference and stay dates in history. Managers can retry one failed guest or select multiple failed rows; each target includes its delivery ID and expected retry_count. Bot cards and notification details submit the exact notice ID. The server rechecks property permissions, locks selected deliveries, excludes sent/uncertain/active/stale attempts, and increments retry_count once per accepted request. Old buttons cannot retry a newer failure. Notice uniqueness includes retry_count so only guests who fail again generate another failure notice; original notices retain their reasons. Retry uses the latest rule/template and live booking data through the same strict worker. Explicit retries bypass old schedule deadlines but retain enabled-rule, cancellation, checkout and final revision checks. The same late-booking policy is rechecked with live reservation data before sending. A successful retry is never automatically repeated.

Calendar Android 1.2.1 (code 7) uses the approved calendar-with-OMS-ring launcher icon as an adaptive vector with the existing blue/navy palette and white background; the notification small icon remains separate. The release keeps the persistent signing certificate for an in-place update.

Late-booking notices: original scheduled time and effective due time are retained separately. A successful exception send creates one `exception` bot notice per attempt, with property, guest, channel, booking reference, original schedule and actual send time. A failed or uncertain attempt never receives a success notice; only its targeted failure/verification notice is emitted. History marks successful late bookings as 예외 발송 완료.

Channel capability: automatic messages use Beds24 channel messaging only. The documented API integrations are Airbnb, Booking.com, Expedia and Vrbo (including its aliases); source IDs distinguish API from iCal imports. Agoda, other unsupported sources, Direct and unverified source metadata fail before the POST, with channel name in the bot notice and manual follow-up guidance. An empty prior message thread is not treated as unsupported. Supported-channel rejections fail normally; transport ambiguity remains uncertain with no automatic retry. No email fallback is implied. Source references: https://wiki.beds24.com/index.php/Messages and https://wiki.beds24.com/index.php/API_V2.0_apisourceids (checked 2026-11-26).


## Password delivery and unresolved failures

- `비밀번호 안내` and `캘린더 발송 표시` are editable only while at least one language contains `{{비밀번호}}`. The server enforces the same rule. Unchecking remains respected while typing.
- Confirmed PIN sends (including an explicit, authorized external-delivery acknowledgement with a live PIN) enqueue an independent `PINSENT` info-item write. Existing booking info is preserved; read-before-write and lease fencing prevent duplicate writes. Calendar API failures back off one hour and never resend the guest message.
- The Beds24 account needs `PINSENT I-key` in Booking Info Codes and Booking Show Icons enabled. This account display preference is separate from the booking API marker.
- Failed/uncertain automatic deliveries create a follow-up. Existing active-stay failures are included; historical schedule exclusions and checked-out stays are not backfilled. Each unresolved follow-up generates at most one reminder per hour through the existing DB watchdog and bot push transport.
- Recipients are the branch's eligible administrators (including authorized shared managers) and currently on-duty employees. Eligibility is checked again before push dispatch; a new shift receives the next reminder.
- `전송 예정임` keeps reminders running without postponing the next due reminder. `다른 방법으로 전송하였음` records manual delivery and stops reminders; for password notices it verifies current PIN and unchanged room/stay before recording evidence. `무시해도 되는 건임` stops reminders and shows exclusion, without claiming delivery or writing PINSENT. Reading an alert does not resolve it.
- The same compact action chooser appears in bot notices, details and home popups. Native notifications open the message screen. All choices are authenticated, recipient scoped, attempt fenced and idempotent. Automatic success resolves the corresponding follow-up.
- `auto_message_followups`, `auto_message_reminders` and `pin_calendar_outbox` are private RLS tables; the action and calendar RPCs are service-role only. No raw PIN is stored in alerts or this outbox.
